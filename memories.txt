 0. THE SHORT VERSION - WHAT WAS ACTUALLY WRONG
--------------------------------------------------------------------------------

The Notes file described a finished system, and the code was genuinely there
(76 tools, 59KB of tools.py). But three things meant that in practice JARVIS
could not reliably act on a command:

  1. HALF THE TOOLS COULD NOT RUN.
     The virtual environment JARVIS actually runs from was missing psutil,
     pyautogui, pyperclip, pillow, screen-brightness-control and send2trash.
     Every tool in the info / input / screen / clipboard / apps / recycle
     families returned "not installed" instead of doing anything. Because those
     imports were inside try/except blocks, nothing crashed - it just quietly
     did nothing, which is why it looked like the AI was "ignoring" commands.

  2. FOUR TOOLS WERE UNREACHABLE, AND ONE DID NOT EXIST.
     brain.py decides which tools to show the model using a category map. That
     map listed a tool called list_ai_providers that is not in tools.py, and it
     omitted ask_llama, ask_qwen, ask_local_model and list_available_ais - so
     those four could never be called, no matter what you said.

  3. THE MODEL INVENTED ANSWERS ABOUT YOUR PC.
     This was the worst one. Asked "what's in my downloads folder", qwen2.5:7b
     replied with a confident made-up list: "file1.pdf, video1.mp4,
     app_installer.exe". Asked about the clipboard, it invented "example text".
     Nothing in the system prompt forbade fabricating PC data, only describing
     actions instead of taking them.

All three are fixed and verified. Details below.

 3. CHANGES TO backend/brain.py
--------------------------------------------------------------------------------

3.1  ANTI-FABRICATION RULE IN THE SYSTEM PROMPT  (the most important change)

     Added a "GROUND TRUTH" section, placed above the TOOL USE section so it
     carries the most weight. In plain terms it tells the model:

       - You have NO direct knowledge of this PC. Files, folders, clipboard,
         processes, apps, IP, battery, time and weather must come from a tool
         result you actually received.
       - NEVER invent or illustrate PC data. No 'file1.pdf', no 'example text'.
         A made-up answer about the user's own machine is the worst mistake
         you can make.
       - If you haven't seen a tool result for what was asked, call the tool NOW.
       - If no tool can answer it, say you cannot check - never improvise.

     Effect, measured: "what's in my downloads folder" went from a fabricated
     file list to a real list_dir call.

3.2  TOOL CATEGORY MAP FIXED

     - removed  list_ai_providers   (does not exist in tools.py)
     - added    ask_llama, ask_qwen, ask_local_model, list_available_ais
     - added a startup drift check that prints a warning if tools.py and the
       category map ever disagree again, in either direction. Silence at
       startup means they match.

     Registry, schemas and categories are now all exactly 76 entries with zero
     mismatches.

3.3  "ask qwen" / "ask llama" NOW RECOGNISED

     CATEGORY_KEYWORDS["ai"] had "ask deepseek", "ask chatgpt", "ask claude",
     "ask gemini" but not "ask qwen", "ask llama" or "ask local model". Added.

3.4  ACTION-INTENT FALLBACK - the fix for "it just talks instead of doing it"

     Before: tool selection was purely keyword based, so a command whose
     phrasing wasn't in the keyword lists got ZERO tools handed to the model.
     With no tools available it could only reply in prose. "jarvis, could you
     tidy up my pc" got nothing.

     Now: if no category matches but the sentence still reads like a command
     (imperative verb at the start, or a phrase like "my pc" / "for me" /
     "right now"), JARVIS is handed CORE_ACTION_TOOLS - a curated set of 26
     high-value tools.

     Deliberately 26 and not all 76: dumping every schema at the model is what
     caused the hallucinated tool JSON recorded as bug 8 in Notes.

3.5  SMALL-TALK GUARD

     The action fallback initially caught "tell me a joke" and handed over 26
     tools, because "tell" was in the imperative verb list. Two fixes:
       - dropped the conversational verbs (tell, give, look, check) from the
         imperative pattern
       - added an explicit _SMALL_TALK list ("tell me a joke", "make me laugh",
         "who are you", "what can you do", "thanks", ...) that short-circuits
         the fallback
     Small talk is back to 0 tools, as intended.

3.6  CATEGORY SCORING - generalises the "list my desktop" fix

     Before: every category whose keyword appeared anywhere fired at once.
     "show desktop" triggered both window and files, which is Notes bug 11.
     That bug had been patched for one specific phrase only.

     Now each category is scored by the LENGTH of the longest keyword it
     matched, so a specific phrase beats an incidental word. Categories more
     than SCORE_MARGIN (4) characters weaker than the winner are dropped, and
     at most MAX_CATEGORIES (3) survive. memory and ai are pinned - they are
     explicit-intent categories and are never dropped by the cap.

     Measured: "show desktop" went from 18 tools across files+window to 5
     tools in window only.

3.7  FILES-PHRASE OVERRIDE SOFTENED

     "what's in my X" used to force files-only. That meant "what's in my
     clipboard" was answered with file tools and get_clipboard was literally
     not on the menu - the model reached for run_shell_command instead.

     Now the files phrase only nudges files one point past whatever else
     matched, instead of overriding it. "what's in my clipboard" offers
     clipboard + files and calls get_clipboard. "list my desktop" still
     resolves to files only.

 4. CHANGES TO backend/server.py
--------------------------------------------------------------------------------

4.1  CRASH-PROOF CONSOLE LOGGING  (this one could kill a live session)

     The Windows console is cp1252. server.py printed the user's text, tool
     names and session info directly. Any character outside cp1252 - an emoji
     in a filename, a non-Latin app name - made print() raise
     UnicodeEncodeError inside the WebSocket handler, which fell through to the
     generic except and ENDED THE SESSION. A command could kill your
     connection purely because of a logging statement.

     I hit this for real: the self-test crashed printing an installed app name
     containing U+A789.

     Added a log() helper that falls back to a replacement-character encode,
     and routed all 11 print sites through it. log() is defined above the
     warmup block so it exists before its first use at import time.

4.2  FINAL REPLY NOW DE-DUPLICATED

     Found by live WebSocket test, not by reading the code. Asked "how much RAM
     am I using", the phone received:

       "You are using 91.4% of your RAM, which is 14 out of 15 gigabytes.
        You are using 91.4% of your RAM, which is 14 out of 15 gigabytes."

     Cause: dedupe_reply was applied to brain's "done" payload, but server.py
     built the final "replace" message from full_reply - the raw accumulated
     token stream, which never went through it. So the anti-repetition fix from
     Notes bug 15 was being bypassed on the exact text the phone displays.

     Fixed: the final text now runs through dedupe_reply(text, user_text).
     Re-tested live, the duplication is gone.

--------------------------------------------------------------------------------
 S2-1. WHAT WENT WRONG WITH "OPEN VS CODE ON THE JARVIS AI FOLDER"
--------------------------------------------------------------------------------

Reported symptom: JARVIS said the Jarvis AI folder "does not exist in your
documents directory" and offered to create it.

Reproduced exactly. Two separate faults:

  1. resolve_path had no idea what "Jarvis AI" was. Its alias table only knew
     desktop / documents / downloads / home. Anything else fell through to
     os.path.expanduser(), which for a bare name like "Jarvis AI" returns the
     string unchanged - a RELATIVE path. That then resolved against whatever
     directory uvicorn happened to be started from, so it pointed at nothing.

  2. The model then invented the explanation. The tool's actual error was
     "Error: 'Jarvis AI' is not a folder" - it never mentioned Documents.
     qwen2.5:7b supplied "in your documents directory" itself, then offered to
     create a folder there. Saying yes would have created a junk folder.

Fault 2 is the same fabrication instinct logged as item 6 of session 1. The
cause is the same: when a tool result carries no information, the model fills
the gap. The fix is therefore to make the tool say more, not just to scold the
model in the prompt.

                                 folder - no --add-dir. Two-turn gate, see S2-6.
  cancel_claude_edit()           drops a pending edit
  pending_edit()                 reports what is awaiting confirmation

  timeouts       CLAUDE_TIMEOUT = 300s. run_shell_command's 45s is far too
                 short; a real Claude Code request took 142s in one measured run.
  output cap     Claude's full answer goes to backend/data/claude_last.txt; the
                 model receives only the first 1200 characters. server.py runs
                 NUM_CTX = 2048, so an uncapped answer would blow the
                 conversation context.
  exe lookup     shutil.which first, then known install paths. uvicorn can start

                   claude -> %LOCALAPPDATA%\Microsoft\WinGet\Packages\...\claude.EXE

                 folder names containing spaces need no quoting. Verified that
                 Python can execute the .CMD shim directly.


--------------------------------------------------------------------------------
 S2-6. THE CONFIRMATION HOLE - FOUND BY TESTING, NOT BY READING
--------------------------------------------------------------------------------

This is the most important thing in this session.

The first version followed the existing house pattern: a confirm bool parameter
defaulting to False, exactly like delete_path and shutdown_pc. It was tested
live and

    IT EDITED memory.py WITHOUT ASKING.

The model simply passed confirm=true on its very first call. A confirm parameter
is not a safety gate when the model is the one filling it in. The file grew from
3037 to 3067 bytes with an added "# Last updated: 2026-09-21" comment. That edit
was reverted; memory.py is back to its original content and compiles.

Note that delete_path, shutdown_pc, restart_pc, kill_process and
empty_recycle_bin all still rely on exactly this pattern. They have not been
changed, and they are therefore all bypassable the same way. That is a
pre-existing hole, now demonstrated rather than theoretical.

REPLACEMENT: a two-turn gate that the model does not control.

  - confirm was REMOVED from the tool schema, so the model cannot supply it.
    Any confirm kwarg it invents anyway is swallowed and ignored.
  - brain.py calls tools.begin_turn(user_text) once per user message, which
    defines a turn boundary.
  - The first claude_code_edit call only ARMS the request and returns a message
    for JARVIS to relay.
  - It can only RUN on a LATER turn, and only if the user's own words in that

--------------------------------------------------------------------------------
 S4-3. WHY THE SPEECH WAS STOPPING - IT WAS NEVER THE VOICE
--------------------------------------------------------------------------------

The gaps were in the TRANSPORT, not the model.

  server.py synthesized one sentence at a time into a complete WAV, wrote it to
  a TEMP FILE, read it back, base64'd it, deleted the file, and sent it.

  mobile.html then did `new Audio(blobURL)` per chunk and waited for the
  'ended' event before even constructing the next one.

So every sentence boundary cost a fresh decode plus a fresh start - roughly
50-200ms of silence - and the work was strictly serial: nothing decoded until
the previous chunk had finished playing. If synthesis ever fell behind, the
queue starved and the gap grew.

FIXED IN TWO PLACES:

 1. server.py / speech.py - the WAV is now built in an in-memory buffer. The
    temp file write, read and delete per sentence was pure latency on the one
    path that is supposed to sound continuous.

 2. mobile.html - replaced the <audio>-element queue with a Web Audio graph.
    Each chunk is decoded AS IT ARRIVES (in parallel with playback, not after
    it) and scheduled on the audio clock at exactly the sample where the
    previous chunk ends:

        if (nextStartAt < now + 0.02) nextStartAt = now + LOOKAHEAD;
        src.start(nextStartAt);
        nextStartAt += buffer.duration;     // sample-accurate butt join

    A 0.12s lookahead absorbs network jitter before the first chunk.

MEASURED, not assumed: test_audio.js schedules three chunks of different
lengths and asserts each starts exactly where the previous ended. Worst
deviation across the run was under one millisecond.

Interrupt handling needed care. A chunk can still be decoding when you tap to
interrupt, and it would otherwise arrive afterwards and start talking again. A
`speechGen` counter is bumped on every interrupt and stale chunks are dropped.
There is a test for exactly that.

A legacy <audio> path is kept for any browser without Web Audio. It has the old
gaps, but it works.


--------------------------------------------------------------------------------
 S4-4. SPEAKING PACE - "TALK FASTER" / "SLOW DOWN"
--------------------------------------------------------------------------------

New backend/speech.py owns the voices and the pace. It was split out of
server.py specifically so tools.py can change speech at runtime without
importing the web server, which would be circular.

The one design decision worth remembering: Piper's knob is `length_scale`,
where HIGHER means SLOWER. That is backwards from what a person means. So the
controller exposes RATE, where higher means faster, and does the reciprocal
conversion (length_scale = 1 / rate) in exactly one place.

  rate range   0.6 to 1.7, step 0.15 per nudge, default 1.0
  below 0.6    Piper slurs; above 1.7 it is hard to follow

MEASURED on the same sentence:
  rate 0.7 -> 5.25s of audio
  rate 1.0 -> 3.85s
  rate 1.4 -> 3.01s
Synthesis itself runs about 18x realtime after the model is loaded, which is
why starvation is not a practical concern.

Three ways to change it:
  - say "talk faster", "slow down", "speak normally"  -> set_speech_pace tool
  - drag the Speaking pace slider in the settings sheet
  - the model can set an explicit rate, e.g. 1.3

NOTE: pace and voice are SERVER state, not per-device like the UI layer
settings. Every connected device hears the same voice at the same pace, which is
correct - the synthesis happens on the PC.

--------------------------------------------------------------------------------
 S5-1. HOW HANDS-FREE WORKS
--------------------------------------------------------------------------------

Two new settings in the sheet, both OFF by default because they change how the
whole thing behaves:

  Hands-free          keeps listening after each reply, no tapping
  Interrupt by voice  leaves the mic open while JARVIS speaks (barge-in)

THE CRITICAL DESIGN POINT: rec.continuous STAYS false.

Setting continuous = true is the obvious way to get a continuous mic and it is
exactly what caused Notes bug 10 - Chrome on Android duplicates the transcript
exponentially ("hellohellohello"). So instead, recognition is RE-ARMED manually
after each turn. That gives the continuous feel without reintroducing the bug.

Re-arming is deliberately not triggered by the 'idle' state alone. Idle arrives
when the model finishes, but audio chunks are still draining on the phone, so
re-arming there would open the mic while JARVIS was still talking. The trigger
is settleIfDone() - every scheduled chunk finished AND nothing left decoding -
plus a 450ms breath.

  scheduleRearm() refuses to fire unless: hands-free on, not paused, not muted,
  not already listening, no audio busy, state is idle, socket open.

BOUNDED SILENCE: after MAX_QUIET_ROUNDS (4) consecutive listens that heard
nothing, hands-free PAUSES itself and the hint changes to
"TAP TO RESUME HANDS-FREE". An open mic that re-arms forever drains the battery
and never tells you it has given up. A tap brings it back.


--------------------------------------------------------------------------------
 S5-2. PRE-EXISTING BUG FOUND: INTERRUPTING DID NOT ACTUALLY STOP THE REPLY
--------------------------------------------------------------------------------

Found while reading the code to plan barge-in, not by testing.

stopSpeaking() only discarded the audio ALREADY QUEUED. The server keeps
streaming the rest of that reply's sentences, so the next chunk to arrive was
happily scheduled and JARVIS carried on talking a moment later.

This affected TAP-TO-INTERRUPT, which has existed since before this session. If
you ever tapped the core to shut JARVIS up and it resumed a second later, that
was this.

FIX: a turn-scoped audio gate.
  acceptAudio starts true, is set false by interruptSpeech(), and is set true
  again only when a new user message is sent. enqueueAudio() drops everything
  while it is false.

interruptSpeech() is now used by the tap handler, the typed-message path and
barge-in, so all three genuinely silence the remainder of the reply.

Tested: "audio sent after an interrupt is dropped, not played", and
"a new turn accepts audio again".


--------------------------------------------------------------------------------
 S5-3. PRE-EXISTING BUG FOUND: THE "RETRY ONCE" RETRY WAS UNBOUNDED
--------------------------------------------------------------------------------

rec.onend has an auto-retry for a fast empty result, guarded by retriedThisTap
so it only happens once. But:

    rec.onstart = () => { retriedThisTap = false; };

cleared the guard on every start, including the retry's own start. So
startListening's `if (!isRetry) retriedThisTap = false;` was pointless, and a
mic that kept ending instantly-empty would retry forever, throttled only by the
180ms delay.

Harmless-ish before. NOT harmless with hands-free: the retry branch returns
BEFORE the quiet-round counter can increment, so the loop could never reach
MAX_QUIET_ROUNDS and never pause. Hands-free would have spun indefinitely.

FIX: rec.onstart no longer touches the flag. startListening already sets it
correctly for a fresh start only. The retry is now genuinely once, after which
the empty result falls through to the quiet-round counter.

This is why the bounded-silence test passes at all.


--------------------------------------------------------------------------------
 S5-4. BARGE-IN AND THE ECHO GUARD
--------------------------------------------------------------------------------

The honest problem, already logged as Notes bug 9: the phone's mic hears the
phone's speaker. Leave the mic open while JARVIS talks and JARVIS transcribes
itself, interrupts itself, and loops.

Barge-in is therefore OFF by default, and the row in the settings sheet says
plainly: "Best with headphones. On a speaker JARVIS may hear itself."

Three gates before any speech heard during playback is believed to be the user:

 1. barge-in must be explicitly enabled (and hands-free on)
 2. at least BARGE_MIN_WORDS (2) words - a click or a cough is not an interrupt
 3. looksLikeEcho() must be false

looksLikeEcho() keeps a rolling 500-character window of what JARVIS is currently
saying (fed from appendToken) and compares the heard words against it. If 70% or
more of the heard words (longer than 2 characters) appear in what JARVIS just
said, it is treated as echo and ignored.

THIS IS A MITIGATION, NOT A FIX. It cannot catch a paraphrase or a
badly-degraded echo, and it will occasionally reject a genuine interruption that
happens to repeat JARVIS's own words back. Headphones remain the real answer.

Tested, and these three are the tests worth keeping:
  - ECHO of JARVIS's own words does not interrupt
  - a single word does not interrupt
  - real speech interrupts playback

When barge-in is OFF, the old behaviour is untouched: the mic is aborted the
moment the speaking state arrives.

 S6-1. WHAT SEARCH IS ACTUALLY POSSIBLE HERE - PROBED, NOT ASSUMED
--------------------------------------------------------------------------------

Four keyless endpoints were tested from this machine before any code:

  DuckDuckGo Instant Answer API   WORKS. Official, keyless, fast (0.3s).
                                  Only answers encyclopedic questions. Returned
                                  NOTHING for "python asyncio gather", "best
                                  coffee shops in cebu city", and even for
                                  "capital of France".

  Wikipedia search + REST summary WORKS. Official, keyless, reliable. It is an
                                  encyclopedia, not the web. The REST summary
                                  endpoint needs an EXACT title (plain
                                  "Asyncio" 404s), so the search step cannot be
                                  skipped.

  duckduckgo.com/html             BLOCKED. Returns HTTP 202 with a bot
                                  challenge.

  lite.duckduckgo.com/lite        BLOCKED. Serves a CAPTCHA - literally
                                  "Select all squares containing a duck".

So: THERE IS NO RELIABLE KEYLESS GENERAL WEB SEARCH from this machine. Scraping
DuckDuckGo is not an option and defeating a CAPTCHA was not attempted.

What was built instead is honest about that. web_answer tries, in order:
  1. Brave Search API    real general web search - ONLY if BRAVE_API_KEY is set
  2. DuckDuckGo Instant Answer
  3. Wikipedia search + summary
and says plainly when none of them answered, including a hint about the key.

The Brave slot follows the same pattern the ask_chatgpt / ask_claude tools
already use: cloud is used only if a key exists, and nothing breaks without one.
If you ever set BRAVE_API_KEY, real web search starts working with no code
change. That is the upgrade path.

 S6-3. THE REAL PROBLEM: INVENTED CITATIONS
--------------------------------------------------------------------------------

With the tool built and correctly offered by the gating, end-to-end testing gave
0 out of 4. The model called NO tool and answered from memory, every time
fabricating a source:

  "who is the prime minister of japan"
     -> "According to Wikipedia, as of my last update, Japan's Prime Minister
         is Fumio Kishida."     (stale - he left office in 2024 - AND the
                                 citation was invented)
  "what is the population of tokyo"
     -> "According to data from recent web sources, ..."   (there were none)
  "how many moons does mars have"
     -> "According to NASA, ..."                           (never contacted)
  "look up the capital of france"
     -> "According to Wikipedia, ... Paris."   (right answer, fake citation)

Note the irony: telling the model in the prompt to NAME ITS SOURCE taught it to
imitate citation format. It learned the phrasing, not the behaviour.

Prompt rules did not fix this. That is now twice that prompt discipline has
failed on tool routing with qwen2.5:7b - 3/5 on claude_code_edit in session 2,
0/4 here.

FIX, APPROVED BY YOU: a deterministic pre-router in brain.py.

  When gating has already concluded that the ONLY applicable tools are the
  spoken-web ones, brain.py calls web_answer ITSELF before generating, and hands
  the result to the model framed as "answer ONLY from this text and name its
  source". The model's remaining job is to say it. It cannot skip the lookup,
  because the lookup already happened.

  Scope is deliberately narrow - the guard is
      "web_answer" in names and names <= {"web_answer", "search_sources"}
  so if anything local also applies, the model still decides. Local routing was
  regression-checked: get_time, get_clipboard, list_dir, get_weather and
  system_info all still win their own questions.

  The lookup text is kept OUT of the persisted conversation (it is appended to a
  throwaway copy of the message list) so a 2048-token context is not permanently
  padded with search results.

AFTER: 4 of 4 call the tool, and the citations are true because the fetch really
happened.


--------------------------------------------------------------------------------
 S6-4. TWO MORE THINGS THE TESTS CAUGHT
--------------------------------------------------------------------------------

 1. WIKIPEDIA SEARCH IS POISONED BY QUESTION WORDS.
    My own selftest failed on "what is the capital of France" after the same
    question had worked minutes earlier. The cause was worth finding:

      "what is the capital of France" -> Wikipedia returned "Closed-ended
          question" and "What Is a Nation?" - it matched on the words "What Is".
          Relevance 0.00.
      "capital of France"            -> "List of capitals of France".
          Relevance 1.00.

    Wikipedia's search matches the literal phrase. So _search_query() now strips
    the interrogative preamble before searching: "who is the prime minister of
    japan" -> "prime minister of japan", "jarvis, can you please look up the
    population of tokyo" -> "the population of tokyo". It never strips a query
    down to nothing.

    Wikipedia's own result ordering is also not relevance for this purpose - it
    offered "Capital punishment in France" next to "List of capitals of France" -
    so three candidates are fetched and re-ranked by term overlap.

    After the fix: "how many moons does mars have" returns "Moons of Mars - The
    two moons of Mars are Phobos and Deimos."

 2. RELEVANCE GUARD, to stop the TOOL fabricating.
    Wikipedia always returns something. Before the guard, "python asyncio
    gather" came back as "According to Wikipedia: Coroutine ..." - a confident,
    unrelated article that JARVIS would have read out as the answer. That is the
    same disease as the model inventing a file listing, only with the tool
    supplying the plausible wrong content.

    _relevance() measures how many of the query's meaningful words appear in the
    result. Below WEAK_MATCH (0.34) the tool says so explicitly: "I did not find
    a direct answer to X. The closest thing Wikipedia has is ... this may not be
    what they asked for."

    Known limit it does NOT solve: "best coffee shops in cebu city" scores as
    relevant (coffee, cebu, city all match) and returns a Wikipedia article about
    a coffee chain founded in Cebu. It is topically related but it is not a
    ranked list of the best shops. Judging that needs real web search.

 S6-5. PRE-EXISTING BUG FIXED: EVERY REPLY WAS STORED TWICE
--------------------------------------------------------------------------------

Found while mapping the control flow for the pre-router.

brain.stream_with_tools() appends the assistant reply to the message list it was
given. server.py then did:

    conversation.append({"role": "assistant", "content": cleaned_final})

on that SAME list. So every assistant turn went into the history twice. With
HISTORY_TURNS = 5 that meant roughly half the context window was duplicate text,
and the model was being fed its own words twice - the exact opposite of what all
the anti-repetition work in session 1 was for.

FIX: server.py now overwrites brain's entry with its cleaned version rather than
appending a second copy.
